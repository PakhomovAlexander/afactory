AF resource management qualification
=====================================

Proposed testing and release contract — revised 2026-10-16
Extends design.txt and the acceptance.csv scenarios. No new feature tests have been executed.

1. Claims to establish
----------------------

The qualification program must demonstrate five things independently:

A. Measurement: AF reports the correct resource, scope, units, observation interval and
   uncertainty. Its admission calculations do not omit ancestors or double-count allocations.
B. Safety: AF does not over-admit its own commitments, start work without authority, release
   reservations contrary to their declared evidence contract or duplicate controlled execution.
   Cooperative retirement is separately checked for truthful residual risk; it does not claim
   that unobserved descendants are absent or enforce a whole-tree resource ceiling.
C. Progress: eligible work eventually advances when the declared conditions for recovery and
   available capacity hold. Bounded-polling ready clients obtain live slots by FIFO hand-off;
large or low-priority eligible work does not starve behind repeated arrivals. Offline/inactive
clients that do not acknowledge offers have no automatic-progress guarantee.
D. Durability: recorded decisions and outcomes survive supported crash/restart paths; unresolved
   external execution remains unresolved until reconciled rather than being guessed away.
E. Explainability: a human can distinguish the cause of a wait, find its evidence and choose
   an appropriate next action. Accurate accounting with misleading diagnostics is a failure.

There is no single green 'resources work' test. A release carries a support/claim matrix whose
cells link to exact evidence. An unsupported backend, untested scenario and passing refusal
are different outcomes. Safety failures block release even if later retries succeed.

2. Test architecture
---------------------

Use a small independent reference model, the actual AF admission/runtime implementation, and
real operating-system/runtime probes. Do not use production decision functions to compute
expected decisions. Sharing wire schemas is acceptable; sharing arithmetic and state transitions
between implementation and oracle defeats independence.

Proposed test components:

* Pure reference model: bounded resource vectors, queue eligibility, reservations, owner
  generations, start claims and terminal observations. Written for clarity, not throughput.
* Deterministic simulation: runs the production scheduler/recovery state machine with injected
  clocks, process/runtime adapters, persistence completion and message delivery. Uses virtual
  time, seeded scheduling, explicit faults and replayable traces. It does not simulate kernel
  memory physics or claim to validate cgroup enforcement.
* Concurrency harness: real separate AF processes against one domain plus focused Rust thread
  interleaving checks. Independent operation history validates admissions and releases.
* Workload probes: small prebuilt programs with explicit start/plateau/finish barriers, bounded
  memory/CPU/I/O/process actions and verifiable effect receipts.
* Independent collector: raw kernel/runtime measurements, identities and monotonic timestamps;
  no AF parsing/aggregation code. Runs outside the tested workload boundary, with its own
  measured allowance and a surviving watchdog.
* Fault controller: injects faults at named transitions and observes they actually occurred.
* Evidence checker: evaluates invariant violations, measurement comparisons, fairness, recovery
  and diagnostic truth; produces one claim report bound to source and executable digests.

A run binds the specification/oracle revision, test binary, AF source/binary, workload binary,
fault schedule, configuration, OS/kernel/runtime versions and capability probe results. Build
on capable runners and transfer exact prebuilt binaries to constrained environments.

3. Formal and generated testing
--------------------------------

3.1 Model the hard protocol first

Use a TLA+/TLC model for the allocation/dispatch/recovery protocol. Begin with two coordinators,
five simultaneously represented requests (two parent/child pairs plus a protected waiter), three
resource dimensions including Task/group slots, policy
generations and crashes. Explicitly model separate domain-store and Task-journal commits, domain
consume/close, remote authorization publication/sealing, duplicate pod claim acquisition and
external start acknowledgments. Parent completion depends on its child; it is not an independent
timer that can conceal a resource wait cycle. Expand bounds as implementation state requires.

Safety properties:
* Every start has a charged reservation, consumed unique claim and a matching durable Task
  permit committed under the valid writer epoch. Writer takeover does not erase committed
  authority. A closed claim cannot start; a consumed claim includes its launcher in recovery.
* No two live owners may grant the same execution identity.
* Same-domain admitted disjoint vectors plus control fit the admitted budget at grant time.
* External allocation shrink is a named state; it does not retroactively make a valid earlier
  grant a scheduler violation, and it prevents new overcommitting grants.
* Unknown/surviving current-allocation execution never frees occupied capacity. Boot/instance
  re-attribution releases only proven-absent current coordinates; authority and other obligations persist.
* released_proven requires whole-boundary termination and sealed future entry.
* retired_cooperative requires its narrower tracked cleanup contract and durable residual-risk
  disclosure; it never satisfies process_tree.complete or process_tree.terminate.
* Nested allocations and retained storage transfers are counted exactly once.
* Pending/canceled requests cannot reappear as new requests under the same idempotency key.
* Token/Attempt budgets and deadlines never increase through retries or resource recovery.

Liveness properties name their assumptions: a live coordinator, eventually functioning durable
storage/backend, stable sufficient capacity, finite existing work and fair processing of enabled
transitions. Under those assumptions an eligible request eventually starts or obtains its
truthful terminal refusal; reconciliation eventually resolves; release eventually becomes
visible. During permanent partition, quarantine is a valid safety outcome, not successful
failover. Model capability absence, too-small allocations and expired authority as refusals.

Record state-space bounds, explored states and liveness settings. Exhaustion of a bounded model
is evidence for that model, not a proof of arbitrary-size production software. Counterexamples
become concrete implementation regressions. Require a state/transition mapping from code to model.

3.2 Test actual Rust decisions and interleavings

Use property-based state-machine tests (for example Proptest) over real production decision
code with the separate oracle. Generate dependency graphs, resource vectors, capacities,
configuration generations, time advances, cancellations and partial observations. Shrink both
inputs and event sequences; retain the minimized trace as well as the seed and generator version.

Test rename/permutation invariance where order is irrelevant, unit normalization, parent/child
conservation, capacity monotonicity for a single fixed request without competing queue changes,
and identical-input replay. Do not assert a global 'more memory never increases latency' rule:
changed admission order can legitimately change contention.

Use Loom for small in-process synchronization components, such as ownership handoff, observer
selection and cancellation-versus-start. It does not validate OS flock, SQLite durability,
interprocess IPC or every possible machine execution. Those need real-process histories and
crash tests. Use explicit barriers rather than sleeps to expose race windows.

Check allocator admission histories for linearizability against the resource-domain model.
Keep invocation/response times, pending calls and committed transaction sequence; timeout is
an unknown operation outcome, not proof it did nothing. The Task/domain/executor protocol is
multi-stage, not one atomic distributed transaction; validate its ordering/fencing invariants
rather than falsely calling the whole protocol linearizable.

4. Measurement calibration
---------------------------

Every observable has a declared measurement contract in measurement-oracles.csv. The test
oracle reads raw interfaces separately from AF and verifies scope IDs and sampling intervals.

Validate three layers separately:

1. Discovery and parsing: exact integer conversion, units, controller availability, parent
   limits, affinity, quotas, quota periods, unlimited values and malformed input handling.
2. Attribution and aggregation: complete descendants, nested scopes, page cache/tmpfs,
   shared data, external use and the difference between memory usage and commitments.
3. Timing and explanation: fresh versus stale, timestamp alignment, peak versus sampled maximum,
   derivation of rates and honest uncertainty in the human/JSON views.

Memory workloads must fault/touch their pages; malloc size alone is not resident usage. Include
anonymous pages, fork/copy-on-write, shared mmap, file cache, tmpfs, swap and short-lived children.
Use plateau barriers for stable comparisons and fresh boundaries or qualified reset semantics
for peak counters. Record allocator/runtime overhead separately from the intended payload.
A sampled high-water mark must never be labelled the true whole-run peak.

CPU workloads include CPU-bound workers, sleeping workers, quota-limited workers and nested
ancestor throttling. Use CPU-time deltas over the matching monotonic interval; raw utilization
may exceed one core. A throttled-duration counter is not automatically a percentage of lost
throughput. A workload doing no useful progress must not appear healthy merely because CPU
is busy. Distinguish quota throttling, scheduler contention and waiting on a provider.

Storage probes cover sparse files, hard links, reflinks where supported, open-but-unlinked
files, quotas, inodes, tmpfs and multiple paths sharing one volume. No source of allocated bytes
is promoted into exact physical ownership where the filesystem cannot provide that information.
Use isolated mounts/volumes for destructive capacity tests; never fill a developer filesystem.

Counter comparison rules:
* Static capability/config values and unit conversion are exact; no percentage tolerance.
* Monotonic counters: bracket the AF sample with independent before/after reads of the same
  boundary/generation and require AF's raw value to lie within that interval.
* Nonmonotonic gauges: use a stable plateau and bounded sampling skew. The initial independent
  calibration establishes a named tolerance from read skew/accounting granularity before the
  candidate is tested. Publish the raw readings and bound; do not widen it after a failed run.
* Missing/unsupported/stale readings stay null with a reason. Zero is never their substitute.
* OOM/process-limit events are checked by event identity/counter deltas and observed lifecycle;
  an exit code or signal alone is insufficient cause attribution.

An independent collector cannot prove the kernel itself is correct. Analytic workload checks
and a second observation source test semantic plausibility; same-source raw comparisons prove
AF interpreted the platform consistently. Report the exact claim each comparison supports.

5. Crash and failover campaign
-------------------------------

Instrument stable failpoints around every persistence/side-effect boundary of the dispatch
protocol. They are test-build facilities, never a production environment-variable bypass.
For each point test immediately before and after the operation, including an acknowledged
commit/start whose acknowledgment is lost to its caller.

Boundaries include queue insert; vector reservation; Task intent append; boundary creation;
execution identity persistence; domain claim arming; atomic Task permit/authority commit;
claim consumption versus closure; execution gate open;
start acknowledgment; receipt capture; descendant stop; empty-boundary confirmation; reservation
release; Task settlement; policy activation; metric/receipt compaction and storage charge transfer.

Fault dimensions:
* Coordinator SIGKILL, observer death, child crash and repeated restart during reconciliation.
* Lease expiry during a long pause; takeover; wall clock jumps; suspend/resume; host reboot.
* Disk ENOSPC/EIO, short writes, delayed fsync, corrupt records and unreadable live reservations.
* Process death after durable commit versus VM power-loss simulation with unsynced writes lost.
* Remote request accepted but response dropped; delayed stale completion; duplicated/out-of-order
  events; API timeout; partition; container/pod/node disappearance.
* Reused PID/path/name and a new container/pod UID occupying a previous display identity.
* Storage restore from an older snapshot while remote work still exists.

SIGKILL is not a power-loss test. Use a fault-injecting persistence adapter/VFS and disposable
VM power-cycle tests to examine persistence assumptions. Respect the actual SQLite synchronous
mode, filesystem and device semantics; an integrity_check pass alone does not prove cross-store
intent correctness. Full-store corruption may require an explicit repair/restore response;
AF must not silently recreate an empty allocator and start new work.

Observe effectful starts with an independent append-only test sink keyed by Attempt, claim and
execution UID. The sink records every invocation without deduplicating it, so the checker can
see duplicate starts that an idempotent target would otherwise hide. It contains no real secret
or paid operation. Distinct authorized retries remain distinct Attempts, with all prior receipts.
Real provider internals remain outside this exactly-once test claim.

Each fault scenario has two phases:
  failure phase: prove no unsafe admission, premature release or unauthorized duplicate;
  recovery phase: heal the declared fault, run a healthy coordinator and prove progress within
  the scenario's finite bound, or the precise remaining dependency that prevents it.

Recovery latency is measured from restored prerequisites to a reconciled visible outcome,
not from fault injection while a service is intentionally unavailable. Report detection,
reconciliation, cleanup and re-admission separately. An attested new boot of the same host/kernel identity proves its old local processes
are gone; migration to another host does not; deleting a remote object does not prove a partitioned node stopped its process.

6. Starvation, fairness and overload
------------------------------------

Use generated workloads plus named deterministic adversarial scenarios:

* Continual small arrivals ahead of one large eligible request.
* Background work beside continuous interactive arrivals.
* Many roots versus many children of one root; repeated new Tasks attempting to reset service.
* CPU-heavy and memory-heavy vectors competing for different scarce dimensions.
* Large parent holding memory while its child needs more capacity.
* More submissions than the queue/coordinator budget and abrupt quota shrink.
* Cancellation/reprioritization while a request owns the protected drain turn.
* Long external pressure followed by a clear healthy period.

Primary metrics: largest accumulated eligible_wait, first admission after a drain turn,
service per root/weight, normalized turnaround, queue length, throughput and control latency.
Report completed, canceled, timed-out and still-waiting requests. Excluding unfinished requests
would hide starvation. Aggregate throughput and a fairness score alone cannot establish progress.

A concrete drain-turn oracle:
  available worker allocation = 3 GiB, separately from the control reserve;
  two initial 1 GiB jobs run; every job live at protection, including admitted backfill,
  finishes within 30 seconds after protection begins;
  a waiting 2 GiB request has no earlier protected waiter;
  small 1 GiB jobs arrive continuously; protect_after = 60 seconds;
  stable capacity, no backend fault, no deadline expiry, scheduler cadence <= 2 seconds;
  live dispatcher immediately acknowledges its claim (ack delay is zero in this fixture).
  The large request must start by 60 + 2 + 30 + 2 = 94 wall-clock virtual seconds from acknowledged eligibility, and no
  new conflicting admission is allowed during its drain turn. Physical runs add only the
  predeclared runner observation/dispatch tolerance, shown in the result.

The reference model determines weighted-service expectations for homogeneous bounded jobs;
physical comparisons allow predeclared granularity for the largest non-preemptible quantum.
Heterogeneous vectors are checked against the scheduler contract, not an invented universal
1:2:4 completion ratio. Deliberately impossible workloads must refuse rather than age forever.

If a stable healthy environment cannot make progress despite eligible work, that is a liveness
failure. During permanent scarcity/partition, accurate waiting/quarantine is the expected safety
behavior; it must not be marketed as successful failover or as proven starvation freedom.

7. Contention and environment matrix
-------------------------------------

Keep the OpenClaw-like resident application as one reference neighbor. Add an interactive
latency probe in a sibling allocation, a competing agent workload, two independent AF commands,
and nested Tasks. Measure neighbor responsiveness as well as AF throughput and OOM outcomes.
Use non-sensitive synthetic inputs for regular tests; bounded real-provider canaries come last.

Qualify:
* Linux delegated cgroup v2, different parent limits, fractional CPU and limited process counts.
* Native cooperative desktop mode, including macOS; strict requests must refuse correctly.
* Docker limited container, executor-created container, no delegated hierarchy, rootless mode
  and Docker Desktop's extra VM boundary.
* Kubernetes coordinator pod and Job executor: namespace quota, Pending scheduling, mutated
  admission limits, eviction, duplicate pod delivery, node isolation and durable state restart.
* Multiple users with externally bounded allocations and no cross-user identity leakage.
* Optional Windows/WSL only with an implemented, declared supported backend.

Use pairwise coverage for routine combinations and explicit high-risk triples: low memory +
CPU throttling + heartbeat; slow disk + crash + pending receipt; namespace partition + duplicate
pod + owner takeover; nested Task + full budget + fairness drain. Pairwise coverage never
replaces named mandatory hazards. Record kernel/controller/runtime features instead of assuming
all containers have the same capabilities.

Stress profiles include 0.25/0.5/2/8 CPU, 512 MiB/1/4/16 GiB, 1/2/8/32 concurrent submissions,
10k and long-history task logs, cold/warm caches, short peaks, sustained pressure and recovery.
Correct refusal on a too-small allocation is tested separately from successful execution.

Linux kernel memory enforcement can have transient accounting overshoot. Tests require correct
limits, scoped events, cleanup and no AF over-admission; they must not assert the physically
false invariant 'observed memory can never exceed memory.max by even one byte'. Cooperative
mode receives no hard-cap protection badge after a sampled no-OOM run.

8. Test the diagnosis and the test system
----------------------------------------

Every injected bottleneck has a ground-truth label and alternative plausible causes. Assert
that explain/status/history reports the correct constraint, scope, age, quantities, owners and
next action. Include mixed bottlenecks and unknown attribution. Provider rate-limit or CLI
compatibility failures must not recommend more RAM. A slow filesystem must not be called full
without capacity evidence. TUI, JSON and exported history must agree on the same read-model prefix.

Mutation controls deliberately break the system under test: omit an ancestor cap, convert KiB
as bytes, use RSS as whole-boundary memory, release on owner death, grant duplicate start,
ignore nested reservations, remove fairness aging, discard fsync failure, hide stale data or
label cooperative enforcement hard. Every named non-equivalent critical mutant must be caught
by its mapped test. Fix the test when it fails to detect the mutant; do not dismiss it as noise.

Test the harness too: watchdog survives coordinator death; effect sink detects duplicates;
collector scope mismatch is rejected; missing fault-trigger acknowledgment makes the test
incomplete; deleting a required result cannot produce a green aggregate. Event counts alone
are insufficient: each fault must reach its intended transition and oracle assertion.

9. Continuous qualification and release gates
---------------------------------------------

qualification-plan.toml defines proposed test tiers and numeric initial budgets. Calibrate
execution cost on a reference runner before enforcing them; a budget timeout is incomplete,
never a pass. Every tier keeps failed attempts and the exact tested identity.

Per change: deterministic regression corpus; bounded formal model; relevant property traces;
thread/interprocess races; measurement parsing; changed backend conformance. No paid inference.
Nightly: rotating deterministic seeds; all mandatory crash boundaries; targeted fault pairs;
real Linux/Docker tests, cooperative desktop lane and bounded sustained contention.
Release: every advertised environment; extended fault campaigns and soaks; measurement
calibration; resource/neighbor latency comparison; bounded Claude and Codex canaries.

Proposed release workload: 24-hour Linux mixed-load soak, 8-hour Docker lane, 8-hour Kubernetes
lane, 8-hour macOS cooperative lane and at least five independent fresh-environment restarts
for each advertised backend. These are engineering coverage targets, not statistical proof.
Do not schedule cloud infrastructure or destructive tests on the production VM implicitly.

A gate passes only when all mandatory checks for its declared support cell ran, all invariant
checks passed, measurement accuracy met predeclared bounds, critical mutation controls were
detected, and raw evidence is complete. A missing capability may be a passing expected-refusal
test but leaves the corresponding enforcement claim unsupported. Skips do not fill support cells.

Retrying infrastructure may establish whether a result is reproducible, but it never deletes
the original failure or turns an unexplained invariant violation green. A known flaky safety
test blocks release until the cause is fixed or its claimed invariant is corrected through
review. No post-result widening of deadlines, tolerances or required environments.

The required test inventory, invariant checker and comparison bounds come from the reviewed
qualification authority, not candidate-controlled output. A candidate may propose harness or
oracle changes, but cannot remove its own failing gate or lower the support requirements.
Test changes require review and retained negative controls; bind both old and new oracle
identities when an accepted semantic change intentionally updates expected behavior.

10. Performance and statistics
--------------------------------

Compare baseline/candidate under the same allocated resources, workload, optimization mode and state
size. Randomize their order in independent blocks and separate cold and warm runs. For absolute
resource overhead and neighbor impact, use the same-candidate static-control build specified in
section20; its deliberate control-process difference is the treatment being measured. Any
separate prior-release regression keeps its own pinned build modes and explicitly costed runs.
Use fixed arrival schedules as well as closed-loop clients so slowdown does not silently
reduce offered load. Report saturation curves and refusals, not only throughput at easy loads.

Preserve per-run data, confidence intervals and unresolved/censored tasks. Report maxima and
percentiles with sample counts and observation duration; do not claim p99 from twenty runs.
Use run-level or time-block analysis for correlated traces. Never treat every two-second sample
of one soak as an independent successful reliability trial.

For zero failures in n independent, identically distributed trials, a one-sided 95% binomial
upper bound is 1 - 0.05^(1/n), approximately 3/n. Twenty clean trials still permit an upper
bound around 13.9%; 3000 give about 0.10%. Those bounds apply only to the defined trial model,
not all production faults or adversarial scheduling. Deterministic seed counts are coverage,
not a direct probability estimate of production failure.

The existing status/admission/observer targets in design.txt remain separate performance gates.
Neighbor responsiveness has a predeclared workload-specific threshold and confidence bound;
a ratio alone is unstable when baseline latency is near zero. Preserve both absolute latency
and ratio. Kernel protection and resource accounting invariants are not relaxed for speed.

After a warm-up, run at least 1000 bounded complete start/finish/reconcile cycles in the leak
fixture. Check live boundaries, processes, file descriptors, scratch allocation, reservations
and retained-state bytes against explicit expected residuals. Tombstones, shared warm caches
and intentionally quarantined executions have named retention rules; they are not blindly
required to be zero. Report growth curves and hard budget compliance. A statistically flat
trend cannot excuse a leaked process or unreachable active evidence.

11. Reproducibility and evidence
--------------------------------

Each run exports:
* source, AF/test/probe/oracle binaries and configuration digests; manifest and schema versions;
* allocation topology, identities, kernel/runtime capabilities, mount/filesystem and clock data;
* random seed and generator version, minimized input trace, explicit fault schedule and hits;
* allocator API history, start-sink observations, raw independent metrics and AF observations;
* before/after reservations, Task prefixes, accounting totals and owned-boundary cleanup proof;
* invariant/measurement/fairness/diagnostic verdicts plus missing evidence and capabilities;
* performance samples, retention limits and an exact replay recipe with no production paths.

Hashes bind evidence to the tested bytes; privileged test helpers cannot be substituted by the
candidate unnoticed. A replay uses the verified disposable account/allocation/rendezvous from section 16, fresh
state, HOME/XDG directories, backend IDs and
fake credentials. It never reconnects to a production provider or deletes real worker groups.
The harness is bounded in CPU/RAM/disk/output and has an independent outer watchdog. Destructive
OOM, disk corruption and node-isolation tests run in disposable owned allocations only.

The test cost is visible: wall/core hours, fixture memory/disk, test outcomes, external runtime
operations and any separately authorized provider spend. A qualification campaign must itself
be a good neighbor and may not use the feature under test as its only safety boundary.

12. Implementation and integration
-----------------------------------

Add the testing interfaces before the new allocator ships: injectable time and effects, stable
failpoint IDs, independent event collection and externally checkable start claims. Build the
reference model and crash reproductions alongside R1/R2, fairness tests with R3, platform probes
with R4-R6 and diagnostic truth checks throughout. R8 aggregates existing evidence instead of
inventing a late end-to-end checklist.

Implement through native AF Tasks in the product repository, respecting AGENTS.md. This draft
adds testing.txt, measurement-oracles.csv, qualification-cases.csv and qualification-plan.toml
beside the feature design. Their scenarios are planned, not evidence of passing implementation.
The original acceptance.csv remains the feature acceptance mapping; new case IDs link to it.

14. Revision-specific adversarial qualification
-----------------------------------------------

Permit race: pause the old writer after checking its lease but before the Task permit commit.
Take over, then resume it: the old commit must fail. Separately pause a launcher after a valid
permit commit, consume-versus-close the domain claim during takeover/cancellation, and resume.
Exactly one transition wins; a consumed launcher remains charged even before its worker exists.
A replacement cannot start until that launcher and its execution are reconciled. Enumerate both
commit orders, lost acknowledgments, cancellation and original-deadline expiry in TLC and the
real process barrier harness. No API guarantees completion of an unobservable remote effect.

Cooperative cleanup: independently witness a tracked child surviving its root, PID reuse, an
unreadable launcher, and an untracked escaping descendant. Surviving/unknown tracked execution
quarantines. All verified tracked identities terminal plus sealed launcher may produce only
retired_cooperative with residual-risk evidence; the witness escape must never yield a proven
empty-tree badge. Run separate macOS and non-delegated Linux cells. Measurement cells state
applicability: per-process native memory, RSS/PSS, tree completeness, pressure and sampled peak
retain their own semantics; absent boundary counters are expected unavailable, not passing zero.

Disk arithmetic: 15 GiB available, 10 GiB floor, two simultaneous 4 GiB growth requests admit
only one. As 2 GiB is allocated, available falls to 13 GiB and that request's outstanding growth
falls to 2 GiB; the second still cannot fit. Deleting that allocation restores both available
space and the possibility of rewrite. Test retained transfer, shared CAS references, unavailable
inode counts, separate state/scratch mounts and quota headroom. An intrinsically oversized
request refuses; temporarily occupied capacity waits only to its original deadline.

Backing placement: reject a 4 GiB memory scratch bound in a 1536 MiB total memory limit before
paid admission. The example succeeds only with declared disk backing and a sufficient volume
reservation. Compare same-host Docker attribution with Docker Desktop/remote execution: never
charge the same resident memory as both AF and outside use, and never pretend separate host/VM
limits are one allocation.

Recovery storage: exhaust ordinary isolated filesystem capacity after preallocating slots and
ballast. Verify bounded final receipt writes and sync under each advertised strict backing
contract, then restart and replay exactly once. Inject metadata allocation failure, short write,
EIO and failed fsync separately. Where durability cannot be obtained, retain prior charged
intents and report unknown final evidence; a missing final receipt cannot become a successful
recovery claim. Repeat with inode exhaustion and multiple registered Task Store volumes.

Fairness: disconnect the protected waiter's dispatcher. A healthy coordinator must suspend its
protection by last pulse write plus sample interval, lease and cadence (4250ms at defaults), preserve age and allow other work.
A live waiter with delayed acknowledgment adds its predeclared ack bound to the 94s fixture.
Policy: race two first activations, restart/reboot, and submit conflicting environment overrides.
Exactly one durable policy generation wins; only explicit config apply changes it. Test priority
above the operator ceiling and reprioritization without resetting service debt.

Kubernetes: hold the claim winner busy while a duplicate loser waits without producing worker
effects or a successful completion. The loser must not trigger winner termination or Task
completion. Inject duplicate supervisor crashes and excess duplicate count; any resulting Job
termination is an explicit interrupted outcome, never false business success or automatic retry.
Use the exact claim-holder pod/container UID for terminal evidence, separately from Job status.
Record version-dependent Job behavior, request/limit mutation and QoS/eviction events.

Closed capabilities: reject misspelled/unknown IDs, aggregate-only proofs offered for per-worker
limits, stale scope identities and strict requests offered cooperative retirement. Verify all
mandatory planned nodes before any paid admission, then recheck exact scope after creation.

15. Review D regression and coverage requirements
-------------------------------------------------

These are planned tests, not executed results. Each acceptance ID must map to at least one
mandatory qualification case; the design checker rejects missing mappings. For full release qualification, expand
that mapping into every advertised applicable support cell and require a real case receipt with
source/binary/capability identities. A missing/skip/unknown receipt cannot satisfy coverage.
Platform-specific claims use their named backend cells; generic safety, refusal, configuration
and privacy contracts apply to every cell. Unsupported platforms demonstrate explicit refusal,
not a success claim. The release matrix must materialize applicability before the campaign;
post-result omission of a failing cell is prohibited. Independent oracle contracts alone are
not executable coverage. Native Review D exposed this gap in the former shape-only checker.

Nested concurrency: hold two roots, each needing more capacity to start a child. Planned maxima
must already be reserved; unplanned expansion must immediately grant or return the typed conflict.
No live-parent resource waiter may remain queued. Repeat with a protected request depending on
one parent's release. Disable deadlines in the finite liveness model so expiry cannot mask a
deadlock; require every ready root eventually to start under finite-holder/stable-capacity/live
client assumptions, including roots temporarily blocked by Task/group slots, and truthful nonblocking
outcomes for unplanned expansion. Test quarantine, stale excess and unreadable Task Store holds:
they cannot support drain eligibility, and unrelated fitting work keeps progressing. Include a
second large eligible waiter: fitting small-job backfill alone does not demonstrate turn fairness.

Dispatcher loss: after acknowledgment inject SIGSTOP, SIGTSTP, a half-open IPC channel and crash.
Process/socket/lock existence must not preserve the turn. At default settings, with a healthy
scheduler, protection disappears by last pulse write + 4.25 seconds; accumulated eligible_wait pauses while
inactive and resumes on rejoin without resetting or preempting an existing turn.
Separately measure live ack/renew latency under the supported 0.25/0.5 CPU, 512 MiB/1 GiB cells
beside CPU/memory/I/O neighbors. Record every latency, sample count, maximum, per-run quantiles,
turn loss, starvation and censored runs. No running result is claimed when readiness correctly
refuses below the measured control minimum. Qualify defaults and acceptance tolerance before
promotion; enforce the 94-second fixture plus its declared acknowledgment allowance.

Remote races: pause before/after domain consume, authorization publication, executor terminal
seal, duplicate-pod selection and gate opening. Race takeover, cancellation and deadline against
each boundary. If close wins no authorization can be published; if consume wins the execution is
possibly live until sealed and reconciled even with no ack. Test delayed old-adapter publication
after sealing. Run the independent model per change and a real supported cluster at release.

Host continuity: replace a coordinator on another node while the old node is partitioned and a
pod-local workload remains alive. A changed boot ID on the new host must not release old work.
Same-host attested reboot can prove old-local termination; ambiguous/cloned host identity cannot.
Recovery transitions include reconciling/quarantined -> retired_cooperative under the narrower
