# ADR-0264: Quarantine flaky tests on gate evidence and confirm them on Claw

**Status:** proposed (2026-10-29).

## Context

The repository's Task gate runs the fast validation profile on a shared host
([ADR-0251](0251-run-the-task-gate-on-the-fast-validation-profile.md)), often at a load average
above 50 on 14 cores. A handful of tests fail there under load and pass alone. The isolation
rerun ([ADR-0205](0205-rerun-a-failed-test-alone-report-the-gate-and-retry-a-failed-gate-on-the-same-candidate.md))
keeps such a failure from failing a gate when the test passes alone, but the same tests keep
failing in other Tasks' gates, every Task pays for their reruns, and one that fails its rerun too
fails a gate whatever the candidate changed. A flaky test is a defect to fix at its cause (`CONTRIBUTING.md`), and the fix
is its own change; the Tasks that keep meeting it meanwhile should not pay for it.

The owner decided (issue #466) that a test which is shown flaky leaves every gate until it is
fixed: no Task gate, no pull request validation and no full release runs it. They set the
thresholds below and named the Claw VM as the host that confirms a flake.

## Considered options

1. Mark flaky tests `#[ignore]`. Rejected: an ignored test is a reviewed manual or child test
   (`.config/test-classes.json` `ignored`) with its own policy; hiding flakes there loses that
   meaning and needs a Rust source change for each entry and each release.
2. Raise the rerun bound or retry a flaky test more often. Rejected: more retries hide a defect
   and cost every gate the time of the retries.
3. A reviewed data file the class resolver reads, with a class that no plan selects, an expiry
   and a bound. Chosen.

## Decision

### The file and the class

- `.config/test-quarantine.json`, schema `af.test-quarantine/1`, holds `tests`: each key an outer
  nextest test identity in the form the catalog's `exact` map uses (`<binary_id> <test name>`),
  each value exactly `state` (`quarantined` or `flaky`), `since` and `expires` (ISO dates,
  `expires` after `since` and at most 14 days after it), `evidence` (a non-empty list of af Task
  IDs) and an optional `issue` (a positive GitHub issue number). It shipped empty. Its JSON
  Schema, `schemas/test-quarantine-v1.json`, is generated by `scripts/test-classes.py` and
  checked for parity by its `audit`, as the class catalog's is.
- `scripts/test-classes.py` classifies a listed identity as `quarantine`, ahead of `exact`,
  `modules`, `binaries` and `overrides`. `quarantine` is not one of the four validation classes,
  so no plan selects it: not the fast profile, not `release:full`, not a label or custom plan.
  Its tests still compile and stay in the audited inventory; the generated nextest filters leave
  them out and keep their siblings. The class report counts a quarantined case in no class row
  and no timing estimate. The plan shape (`af.test-plan/2`) is unchanged, so an empty file
  selects exactly what the catalog alone selected.
- The full gate's one unplanned nextest run, the `test` recipe that `make check` and
  `scripts/verify.sh --profile full` reach, starts through `scripts/test-classes.py nextest-gate`,
  which validates the file and appends `-E 'not (<the quarantined identities>)'` to
  `scripts/nextest-gate.py`'s arguments; with the file empty it passes them unchanged. The class
  runs of the fast profile and of a plan use the generated filters above. `make test-repeat`
  (an explicit `NEXTEST_FILTER`), a direct `cargo nextest run` and the `TEST_RUNNER=cargo`
  comparison path, which no gate profile uses, still run a quarantined test: they are where a
  developer reproduces and fixes one.
- Quarantine covers the default-feature inventory only. The fixed selectors of the feature
  builds (`review-core` `perf_` and `review-pipeline::perf_probe` `calibration_build`, run by the
  perf class's feature variants and by `make check`'s `perf-feature-tests`) take no exclusion, so
  an identity they reach, including one that exists only in a feature build, is refused: fix the
  test, or exclude it from its feature selector by hand.

### The guards

`scripts/test-classes.py audit`, the `test-catalog` step of `make check` and of the base check,
and every plan and class run, refuse with a message naming the entry and the fix:

- a file of another shape, an unknown or missing field, a bad state, a bad date, a window longer
  than 14 days, empty evidence or a bad issue number;
- an entry whose `expires` is before today (`AF_TEST_QUARANTINE_TODAY=YYYY-MM-DD` replaces the
  clock, so no test depends on it);
- more than 20 entries;
- an entry that names an `#[ignore]` test, or an identity no catalog rule classifies;
- an identity a feature build's fixed selector reaches, with the message that quarantine covers
  the default-feature inventory only;
- at partition time, where the compiled inventory is known, an identity not in it or ignored
  there.

### The three processes

1. **Quarantine on gate evidence** (Q2, a scan script; not built yet). A test is added as
   `quarantined` when the structured check reports of at least 2 distinct Tasks' gates within
   7 days list it as flaky. `evidence` names those Tasks; `expires` is `since` plus 14 days.
2. **Confirm on Claw** (Q3, a confirmation script and runbook; not built yet). The Claw VM, for
   now the one confirmation host, runs the entry's test 50 times under load through the gate's
   own scheduling (`scripts/nextest-gate.py --repeat`). A failure confirms it: the state becomes
   `flaky` and an issue is filed for its fix. 50 passes release it: the entry is removed and the
   test returns to the gate, except under the platform rule below.
3. **Fix separately.** A fix is its own change that removes the entry, proven as
   `CONTRIBUTING.md` asks (`make test-repeat`, the stress proof). An entry that reaches
   `expires` unfixed fails `make check` until someone removes it or renews it on new evidence;
   at most 20 entries keep quarantine from becoming a second, unreviewed ignore list.

### The platform risk

Claw is Linux. A flake seen only in macOS gates may not reproduce there, and 50 clean Linux runs
would release a test that still fails every macOS gate. The rule: an entry whose evidence comes
only from macOS gates is never released by a clean Claw confirmation. It stays `quarantined`
until a fix removes it or it expires; on expiry it returns to the gate, and fresh macOS evidence
quarantines it again. The confirmation script reads the platform from each evidence Task's check
report; the entry does not repeat it.

### Only structured reports are evidence

The scan reads the `flaky` list of each Task's structured check report (`af/TaskCheckReport@1`,
`checks.<name>.tests.flaky`), never a gate's text output. `crates/af/tests/it/task_gate.rs`
prints fixture lines such as `flaky: gate-store-regression fails_when_crowded` and
`failed twice: gate-store-regression many_0` inside the output of a real gate, and af 0.13.0's
text fallback read those fixture names as the gate's own flaky tests (#436). An identity taken
from text would quarantine a test that does not exist, or one that never flaked.

**Amended 2026-10-30** ([#466](https://github.com/PakhomovAlexander/afactory/issues/466), Q2).
No command gives the scan the structured report alone: an `af task list --json` row's
`gate.flaky` does not say whether its names came from the report or the text fallback, and
`af task show --checks --json` deliberately omits `evidence`. What counts now is the list rows'
flaky names, admitted only through inventory resolution: `scripts/test-quarantine.py scan` takes
a name as evidence only when it resolves to exactly one identity of the default-feature nextest
inventory, as that `<binary_id> <test name>` exactly or as a bare test name exactly one identity
carries (af 0.13.0's fallback drops the binary), and never to an `#[ignore]` test or one a
feature build's fixed selector reaches. Fixture names still cannot enter: `gate-store-regression`,
`fails_when_crowded`, `af::it` and `many_0` name no test of the inventory, so they never resolve
and the scan lists them as rejected. A real test the fallback reports flaky without its gate
having rerun it is a false positive this rule admits; Q3's confirmation catches it, removing an
entry whose test never fails in its 50 runs.

**Amended 2026-10-30** ([#466](https://github.com/PakhomovAlexander/afactory/issues/466), Q3).
The confirmation is `scripts/test-quarantine.py confirm`, and its report is applied by
`scripts/test-quarantine.py apply`. It does not run `scripts/nextest-gate.py --repeat`, whose
runs stop at the first failure: it runs N whole runs (50 by default) of an exact filter through
`nextest-gate.py`'s run, with `--no-fail-fast --retries 0`, never stopping early and never
rerunning a failure alone. The functional class's selection runs in a loop beside them as the
load. An identity that failed in some runs is `flaky`. One that failed in every run is
`always_fails`: its entry is removed and a P0 issue filed, because main is broken. One that never
failed is `clean`. The report (`af.test-quarantine-confirm/1`) records the host's
`platform.system()`. The platform rule cannot read the platform of each evidence Task's check
report: the list rows the scan reads carry none, and the entry does not repeat it. So the evidence
platform is an argument of `apply`, `--evidence-platform`, defaulting to macOS (`Darwin`),
because this repository's af gates run locally on macOS. A clean report from a host whose
`platform.system()` differs keeps the entry `quarantined` with its dates untouched. A clean macOS
confirmation, run locally, releases it. The runbook is
[`docs/test-quarantine-claw.md`](../test-quarantine-claw.md).

## Consequences

- A flaky test costs the gates that met it, then leaves every gate until it is fixed or its 14
  days pass. While quarantined it guards nothing in any gate, PR or release validation: the bound
  of 20 and the expiry bound that loss.
- The file is reviewed data like the catalog; adding, renewing or removing an entry is a pull
  request that `make check` validates.
- Until Q2 and Q3 exist, entries are added and removed by hand under the same thresholds.
- `docs/test-classes.md` ("Quarantine") documents the file, the class and the guards.
