# ADR-2026-11-11-issue-oriented-operator-pipelines: Replace operator execution selections

Status: proposed
Date: 2026-11-11

## Context

The operator catalog offers overlapping default, light, Pi, warm and kernel execution
families. They do not express whether diagnosis, design or measured experimentation is
required, and local slot replacements can obscure effective roles. Workers cannot edit trusted
`.af/` authority. Captured historical Tasks retain their own package bytes and spending.

## Options

- Keep old names as aliases: rejected because two selectable catalogs would conceal migration
  mistakes and make routing ambiguous.
- Rename an ordinary implementation graph to research, design or performance: rejected because
  prompts cannot supply independently accepted Documents or kernel Measurements.
- Put report operators inside an implementation Task: rejected because the installed native
  profiles have different operator sets. Adding a combined profile is unnecessary.
- Stage a complete consuming catalog and compose existing native Tasks: selected. Installation
  remains an explicit reviewed authority change after this candidate verifies.

## Decision

Stage the seven selections in `fixtures/issue-workflows/selections.json`, with pinned native
packages, one shared read-only verification capability and a complete replacement catalog and
settings. Remove superseded execution families from replacement authority without aliases.
Preserve the independent backlog triage service. Generic product onboarding is unchanged.

Diagnosis and design are native Report Tasks: independent verification and report acceptance
precede a required Document input to implementation. One native Scenario per selection binds the
accepted report and final candidate through typed fresh-Task predecessors. Native admission
checks the exact accepted result, original source and report size. Each stage retains its own
kind-specific authority pin on the same source commit. No Scenario Action, remote adapter or
publication authority is included.

Performance uses real baseline and candidate Measurements, deterministic Comparison and a
comparison-aware evaluator after independent code Review. Its required goal coverage ends at
measurement acceptance. Candidate measurement and comparison outputs are optional because earlier
checks can fail; absence cannot satisfy the required goal result. The committed `release_build`
measure and objective define this initial bounded workload, not arbitrary optimization claims.

Codex roles use personal aliases: Sol medium implementation, Terra high bugs, Sol high
correctness and Astra medium evaluation. Light uses one Terra high reviewer and Sol medium
evaluation; its Kimi variant changes only implementation to Pi `kimi-coding/k3.1-pro` high.
Investigation uses Sol high; design uses Astra medium with independent Terra high verification.
Local native kernel and Markdown gates remain mandatory. There is no advisory Worker.
The existing shared Review policy's optional bugs *policy entry* remains necessary for a light
Round that binds only correctness. Default graphs bind bugs and correctness to the native reducer;
missing bound results still fail closure. This does not promote advisory benchmark Demands to
required Demands or claim a new per-Pipeline Review policy capability.

The launcher refuses retired names, checks explicit light routing facts and exact effective plan
roles and package closure, and emits a read-only migration manifest. It does not infer semantic
scope from filenames. Light allows one implementation Attempt; automatic repair is absent and
launcher continuation is refused. A manually authorized repair must retain cumulative ancestry,
use default verification of the whole candidate and stay within the pilot's two-Task light bound.
Captured Tasks and Stores are never rewritten or deleted. Account bindings remain machine-local;
model definitions and routing remain versioned.

## Consequences

The root operator must install and commit staged authority after verification, quiesce active work
before switching machine-local selections, and explicitly authorize each native Scenario pin.
Existing captured plans continue on their original bytes; historical artifacts are not aliases
for new execution choices. Pilot manifests retain issue, PR, source, Task and plan identities and
cumulative charges, including unknown usage separately. Fixtures prove planning and dataflow,
not live quality, speed or savings. Live bounded pilots remain owner work.
