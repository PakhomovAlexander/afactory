# Frozen legacy review bundles — private, per-hub

This directory holds frozen `/self-review-heavy` bundles: real reviewer output captured
from real runs, used as the acceptance corpus for the kernel's contracts
(`crates/review-core/tests/legacy_corpus.rs`) and the ledger importer
(`crates/review-store/tests/legacy_ledgers.rs`).

**The template ships none.** A review bundle contains real findings about real code —
private project data that must not travel with a public template. The tests that read
this directory are `#[ignore]`d — cargo prints `ignored`, which a reader can see, where a
runtime skip would print `ok` and hide the reason. A hub that has captured a corpus runs
them with `make review-kernel-test-corpus`; there, a missing corpus fails.

That skip is not a coverage hole, because it is not the only coverage. The same contracts
are asserted in every checkout against `../synthetic/`, whose `input/*.json` and
`ledger.jsonl` are real output of the real harness and carry nothing private. What a
private corpus adds on top is acceptance against *reviewer* output — real models writing
real findings about real code — which no generated fixture can stand in for.

## The layout the tests look for

Nothing generates this layout any more — the v1 orchestration that wrote per-stage findings
files is retired — so a bundle is assembled by hand, and the tests look for exactly this:

```text
fixtures/legacy/<bundle-name>/
  findings-<stage>.json     one reviewer stage's output, the shape findings.schema.json
                            describes; read by crates/review-core/tests/legacy_corpus.rs
  ledger.jsonl              the run's final ledger, one row per line; read by
    (or ledger/ledger.jsonl)  crates/review-store/tests/legacy_ledgers.rs
```

A bundle missing both files is simply not picked up. Neither test infers anything from the
directory name.

## Capturing a corpus in your hub

Read the layout above first: the tests want `findings-<stage>.json` and `ledger.jsonl`, and
**nothing in this repository writes either of them.**

- `bundle.sh` captures the *change under review* — `diff.patch`, `files.txt`, `stats.txt`,
  `commits.txt`, `meta.env`, `untracked.txt`, and the test-selection lists. Useful context to
  freeze alongside a corpus, but on its own it is not one: it writes neither file the tests
  read.
- The stage outputs came from the v1 orchestration, which wrote each reviewer's JSON into the
  bundle directory. That orchestration is retired, so nothing produces them today.
- `ledger.sh` still writes `ledger.jsonl`, so a run driven through the legacy scripts still
  produces that half.
- A **kernel** campaign stores its findings in `.review/runs/<campaign>/` as an event log plus
  a CAS, not as either file. There is no exporter from that shape to this one.

So a corpus here is historical: a hub that already has v1-era bundles can freeze them, and a
hub that started on the kernel will simply never have one. That is expected — the contract is
covered in every checkout by `../synthetic/`, and this directory only adds acceptance against
real *reviewer* output when a hub happens to hold some.

To freeze one:

1. Copy the bundle directory in verbatim, never edited. A fixture that has been "fixed"
   proves nothing.
2. Make sure it carries `findings-<stage>.json` and/or `ledger.jsonl` — a directory with
   neither is silently not picked up.
3. Record integrity: regenerate `SHA256SUMS`, and verify with `shasum -c SHA256SUMS` from
   this directory.
4. Run `make review-kernel-test-corpus`, which fails rather than skips if the corpus is not
   found.

The synthetic corpus under `../synthetic/` (generated by running the real harness on
constructed cases) and the adversarial specs under `../adversarial/` ship with the
template and carry the behavioral coverage; this directory adds real-output acceptance
on top when you have it.
